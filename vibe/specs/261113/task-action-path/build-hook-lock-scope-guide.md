## 4. 执行顺序与完成条件

### 4.1 先建立可撤销的任务范围

拟区分 `development / read-only / existing-package / unknown`。范围登记由执行者在既有任务内完成，不要求用户逐轮重复确认，不建立第二套任务系统。

1. 明确项目检出、既有任务引用、当前有效范围及其失效条件。只保存必要状态和摘要，不保存原始提示、聊天、命令、工具输出或凭据。
2. 每次进入构建前核对最新范围。用户改为只读、只要方案、停止、缩小写集时，先使旧开发范围失效并禁止新动作，再停止相关执行者、核清在途结果；不能在等待执行者退出期间继续沿用旧授权。
3. 仓库 dirty、缓存缺失、别人改了源码、进入了项目目录，都不是本轮开发授权。
4. 已知本任务交付源码时，即使写入来自 shell、子 Agent 或外部编辑器，也保持开发核验责任；缺证据时记“待核验”，不能借 `unknown` 宣布交付完成。
5. 未证明属于开发任务时，不获取构建锁、不创建成功基线；只读排除也不得写构建回执。范围登记本身不是只读任务必须执行的写操作。

完成条件：本任务的明确开发入口仍能被检查，而纯只读、发已有包和暂停后的回合不会因其他任务的变化构建。

### 4.2 构建互斥与共享终态

1. 保留原子抢锁；元数据含唯一持有标记、构建编号、持有进程及可验证的进程身份、开始时间、输入摘要、环境键和终态回执引用。
2. 占锁时绑定实际持有的构建编号，拟等待上限30秒；不是每次轮询重新计时。元数据尚未写完、读取失败或旧锁没有元数据，不能当作无锁。
3. 等待者通过对应构建的终态与当前输入核对结果，避免中间结果、另一次构建或被覆盖的共享 state 冒充原结果。
4. 输入及环境相同、产物仍匹配时复用成功；匹配尝试已失败时共享失败，不启动同输入的第二次自动构建。内部失败分类和构建编号可共享，不保存原始构建输出。
5. 等待期间输入或环境改变，重新计算构建键。只有仍有效的开发范围可排入下一次构建；原成功不能替代变化后的核验。等待结束、获得锁后、实际启动build前再次核对当前范围；若范围已失效，停止启动并仅释放自己持有的锁。
6. 等待超时记 `pending`，持有者异常或结果无法确认记 `unknown`；两者都不等于失败或通过，也不自动反复 block 催查。
7. 只由持有者清理自己的锁；进程退出、PID复用、元数据损坏、异常退出后遗留锁均先核验。不按锁龄自动删除，不终止未知进程。
8. 将等待、最长构建、终止清理及状态写入纳入现有660秒总预算；不足时先调整内部预算，不默默扩大宿主超时。
9. 回执更新保留已写的必要阶段字段；裁剪不删除活动或被引用记录，回收后再恢复到历史数量上限。并发回执使用各自文件和可区分的临时写入名。

拟区分等待、运行、重建成功、复用成功、实际失败、待核验和未知；最终枚举在类型、实现、测试和规则中保持一致。未知与超时不消耗“实际构建失败”的自动续接次数。

自动入口与受管理的手动核验共用检查器。保留完整 `npm run build` 链路；原始命令的直接执行不天然受当前锁保护，说明文档必须明示该边界，不在本任务中改造所有外部构建方式。

### 4.3 分发证据与包身份

1. 保留当前选包与发送目标；选定后固定本次副本，从该副本计算 SHA-256、字节数并读取包内身份，实际上传也使用该副本。
2. 身份字段为 `coreVersion / hostAssetId / rendererAssetId / builtAt`。静态、有界读取，不执行 JS、不安装、不重启，不把包解压到运行目录。
3. 解析格式与位置以样包证据为准；遇多份冲突身份、损坏或缺字段，明确报告不可核验，不从本地 public 或 dist 补填。
4. 保留发送指定已有包的能力；身份不可读时可以只证明传输一致，不能静默新增“旧包全部禁止发送”的规则。
5. 用户明确要求发送指定修复版本时，先绑定对应期望摘要或身份。不匹配，或要求的身份无法核验时，暂停该次发送并说明。若仅要求指定SHA-256且摘要匹配，不因包身份不可读额外拒发；明确同时要求身份时还须核对身份。未指定版本时不擅自要求它与当前源码一致。
6. 同摘要跳过和实际上传分别报告，均绑定同一包摘要；摘要相同证明文件一致，不能证明来源真实、代码安全或安装加载成功。
7. 保留已有目标变更检测。检查与替换之间可能存在并发窗口，不宣称目标永久稳定；新增远端目标锁不在当前写集内，若实测证明需要，另列建议。

## 6. 主控核查与真实验证

下表是后续实施的定向验收设计，全部未执行。当前文档阶段只做源码静态对照和链接检查；不以本表授权当前测试、构建、传包或宿主操作。

| 序号 | 必须比对的场景 | 预期与证据 |
| --- | --- | --- |
| 1 | 两个有效开发请求，同输入并发 | 只执行一次build；第二请求关联同一编号，预算内取得终态则复用，超时则pending且不另启构建 |
| 2 | 原构建失败，另一会话等待 | 共享实际失败；不立即再次自动构建同输入 |
| 3 | 等待期间输入改变 | 旧成功不算新输入通过；新构建仍须有效开发范围 |
| 4 | 等待超时、异常持有者、PID复用或旧锁缺元数据 | 返回明确pending/unknown；不误报失败/成功，不删未知锁 |
| 5 | 正常释放后另一构建立刻获锁 | 等待者不误认新持有者为原构建，按编号读取结果 |
| 6 | 回执达到100份且仍有活动等待者 | 活动记录不被裁剪；并发写入不会串用临时文件 |
| 7 | 首次进入的只读或已有包分发任务、缓存缺失、他人dirty | 不构建、不抢锁、不建成功基线；已知开发责任不借此消失 |
| 8 | 用户在派发后改成只读/只要方案/停止，或排队等待期间收窄范围 | 先使旧范围失效并禁止新动作，再停止原执行者并回报；等待者获得锁后也不启动build，随后Stop不恢复开发 |
| 9 | shell、子 Agent、外部编辑器交付源码 | 主控汇总到同一开发责任；缺本地patch不能被当作无需核验 |
| 10 | 旧成功产物损坏、构建中输入变化、产物缺失 | 保留原拒绝成功断言；不通过放宽旧测试取得绿色 |
| 11 | 同输入构建失败，环境修复后显式重新核验 | 新尝试可辨认；自动请求仍抑制无效重复 |
| 12 | 所选包身份与当前dist不同；身份缺失或冲突 | 从实际副本取证；保留仅传指定已有包能力，明确身份未验 |
| 13 | 用户指定版本/身份不匹配或无法核验；仅指定摘要且匹配 | 前者在上传前暂停，不自动build替换候选；后者不因身份不可读额外拒发 |
| 14 | 同摘要跳过、上传成功、上传校验失败 | 分别回报，绑定实际副本；不把传输结果当作安装验收 |
| 15 | 真正宿主Stop、手动检查器、受控并发 | 分别留最小证据；`source=hook`标签或手动模拟不能单独冒充真实Stop |

主控对照顺序：认可范围 → 派发写集 → 实际diff → 保留行为 → 定向检查 → 真实入口与产物 → 未验项。输入或版本变化只使相关证据失效，不为包装收尾重复跑全套检查。

主控接受须同时满足：写集未扩大；实际行为符合本指导；失败与未知如实保留；证据绑定当前输入/包；必要检查已完成；用户保留的宿主验收仍单列。通过静态检查不能把实现标为运行通过，通过build不能把包标为已发送或已加载。

## 7. 防偏差与后续改进

| 序号 | 易发生的偏差 | 预防与发现后的动作 |
| --- | --- | --- |
| 1 | 只看整体方案认可就开始执行未收敛设计 | 当前阶段保持文档与审查；按4.1的可行性证据确定实现，再派发具体写集 |
| 2 | 为修误触发，把unknown当成只读或成功 | 已知开发责任保持待核验；未知不授予构建权，也不解除已有交付门禁 |
| 3 | 只等锁释放，没有共享失败和编号 | 按第6节验收表的第1、2、5项联合验收，不以“没并行”一项代替完整结果 |
| 4 | 超时后递归重试或连续block形成新循环 | 单一等待预算，结果明确pending，不自动续接重试 |
| 5 | 通过删锁、放宽类型/构建门禁或删断言求通过 | 保留原完整链路和拒绝条件；方案支持的预期变化之外全部逐项比对 |
| 6 | 包无法解析便扩成所有旧包拒发 | 仅报告证据不足；严格版本发送须来自明确版本要求 |
| 7 | 顺手新增远端锁、打包器或全局规则 | 只记独立建议及证据，不混入当前实现；发现必要性变化先上报 |
| 8 | 测试/子Agent回报替代真实宿主结果 | 区分reported、静态已查、定向已验、真实入口已验和最终接受，不补写缺失状态 |
| 9 | 执行途中用户收窄范围，回执仍沿旧计划 | 先使旧范围失效、禁止新动作，再停止相关执行者并核清在途结果；保留无关dirty，仅在新范围内继续 |

后续改进只记有证据的条目：现象、对应输入/构建编号或包摘要、复现条件、原因是否已证、最小建议、影响范围与待验证项。P1偏离认可范围的事项先纠正；P2可选改进不作为当前交付隐含门槛。不得自动修改全局规则、记忆或启动下一轮开发。
